\paragraph{R2D2: Feature Detector Summary}
For the first feature detector, I chose the R2D2 detector from \cite{r2d2}. The R2D2 detector-descriptor is a CNN-based method that jointly predicts (1) a repeatability heatmap \(R(\mathbf{x})\), (2) a 
reliability/confidence map \(S(\mathbf{x})\), and (3) dense descriptors \(D(\mathbf{x})\) over the image. Keypoints are produced 
by selecting spatial local maxima of the repeatability map and then filtering those candidates by reliability:
\[
\mathcal{K} = \{\,\mathbf{x} \mid R(\mathbf{x}) \text{ is a local maximum and } S(\mathbf{x})>\tau\,\},
\]
where \(\tau\) is a threshold controlling how reliable a detected point must be to be kept. Descriptors are sampled from the dense 
descriptor field and L2-normalized:
\[
\mathbf{d}(\mathbf{x}) = \frac{D(\mathbf{x})}{\lVert D(\mathbf{x})\rVert_2}.
\]
During training, R2D2 optimizes three complementary objectives: a descriptor matching loss that encourages descriptors at corresponding 
locations to be similar, a repeatability loss that encourages stable local maxima under geometric/image transformations, and a 
reliability loss that predicts whether a detected keypoint will yield a correct match. In practice, this yields sparse keypoints 
that are both repeatable across views and predictable to match (high reliability), which improves downstream matching quality compared 
with detectors that report only corner strength or only descriptor distinctiveness.

\paragraph{R2D2: Unreliable Keypoints}

textured surfaces, and high-contrast areas. The clustering of keypoints occurs because R2D2 
detects features across multiple scales, which can lead to overlapping detections when strong 
structures are present at several pyramid levels. However, there are still few keypoints that lie in regions that have less distinct or repetitive features, such as the ones

\subsubsection{Feature Matching}

The feature matching pipeline used in this part is implemented across three scripts in the repository:
	\texttt{tools/R2D2.py}, \texttt{tools/matcher.py}, and \texttt{starter\_code\_feature.py}. The following summarizes the
implementation, parameters, and the filtering rules applied during matching and depth computation.

\paragraph{Overview}
\begin{itemize}
    \item \texttt{tools/R2D2.py:} performs feature detection and descriptor extraction using the R2D2 framework \cite{r2d2}. It produces
        per-image files containing \texttt{keypoints} (pixel coordinates and scale), \texttt{descriptors} (128-d vectors), and
        \texttt{scores} (reliability values).
    \item \texttt{tools/matcher.py:} implements brute-force L2 nearest-neighbour matching with Lowe's ratio test and simple
        geometric constraints (vertical epipolar tolerance and disparity sign).
    \item \texttt{starter\_code\_feature.py:} performs feature extraction and matching, computes disparity and depth using
        stereo calibration, writes the sparse depth predictions to \texttt{P3\_result.txt}, and
        generates visualizations.
    \item \texttt{tools/calculate\_depth\_error.py:} calculate depth errors from the ground truth depth for training images.
    
\end{itemize}

\paragraph{Feature extraction (\texttt{tools/R2D2.py})}
The R2D2 extractor is invoked (via \texttt{r2d2/extract.py}) to produce a sidecar \texttt{.r2d2} file per image. Each
file stores arrays loaded with NumPy:
$ \text{keypoints}\in\mathbb{R}^{N\times 3},\quad\text{descriptors}\in\mathbb{R}^{N\times 128},\quad\text{scores}\in\mathbb{R}^N.$
Keypoints are in pixel coordinates $(u,v)$ and include a scale value.

\paragraph{Descriptor matching (\texttt{tools/matcher.py})}
Let $L$ denote left descriptors and $R$ denote right descriptors. Matching proceeds as follows:
\begin{enumerate}
    \item Compute the pairwise L2 distance matrix $D\in\mathbb{R}^{|L|\times|R|}$ with entries $D_{ij}=\lVert d^L_i-d^R_j\rVert_2$.
    \item For each left descriptor find the nearest and second-nearest right descriptors ($j_1, j_2$) and associated distances
        $d_0=D_{i,j_1}$ and $d_1=D_{i,j_2}$.
    \item Apply Lowe's ratio test and a distance threshold:
        \[\text{ratio\_mask}_i = (d_0/d_1 < \tau_{\mathrm{ratio}}) \;\wedge\; (d_0 \le \tau_{\mathrm{dist}}).\]
        Default code parameters: $\tau_{\mathrm{ratio}}=0.9$, $\tau_{\mathrm{dist}}=5.0$.
    \item Enforce an epipolar constraint: $|v^L_i - v^R_{j_1}| < \epsilon_y$ with $\epsilon_y=2$.
    \item Filter out negative disparities: $u^R_{j_1} < u^L_i$.
    \item The final mask is the conjunction of the ratio, epipolar and disparity masks; matches and their descriptor distances
        are returned as arrays.
\end{enumerate}

\paragraph{Disparity and depth (\texttt{starter\_code\_feature.py})}
For each accepted match (left index $i$, right index $j$) the pixel coordinates are extracted and disparity is computed as
\[\text{disparity} = u_L - u_R.\]
Depth is then estimated from stereo geometry via
\[ z = \frac{f\cdot B}{\text{disparity}},\]
where $f$ is the focal length and $B$ is the baseline obtained by factorizing the projection matrices
(from the built-in classes: \texttt{krt\_from\_p} and \texttt{get\_stereo\_calibration}).

\paragraph{Filtering rules}
As stated in the handout, to avoid invalid or very noisy depth estimates, the implementation applies the following filters:
\begin{itemize}
    \item Skip matches with disparity $\le 0.1$ (prevents division by zero).
    \item Discard depths $z>80\,$m or $z<0$ (long-range predictions are unreliable for evaluation).
\end{itemize}

\paragraph{Output and visualization}
Filtered sparse depth predictions are written to \texttt{P3\_result.txt} with the format
	\texttt{(image\_id u v disparity depth)}. Visualizations are created using OpenCV's \texttt{cv.drawMatches}.

\subsubsection{Outlier Rejection}

\paragraph{RANSAC-based Outlier Rejection}

To improve geometric consistency beyond the simple epipolar vertical-tolerance test, I ran RANSAC to estimate the fundamental matrix from 
tentative descriptor matches and reject the outliers. The added RANSAC stage performs the following steps:

\begin{enumerate}
    \item Build tentative matches using brute-force L2 nearest-neighbour matching with Lowe's ratio test. (Same as the previous approach.)
    \item Convert matched pixel coordinates to homogeneous points:
    \[
      \mathbf{x}_1 = [u_1, v_1, 1]^T,\quad \mathbf{x}_2 = [u_2, v_2, 1]^T.
    \]
    \item Estimate the fundamental matrix $F$ using RANSAC with the \texttt{cv.findFundamentalMat()} \\ function:
    \[
      F = \texttt{findFundamentalMat}(\{\mathbf{x}_1\},\{\mathbf{x}_2\};\ \texttt{method}=\texttt{FM\_RANSAC},\ \tau_{\text{ransac}},\ \text{conf}).
    \]
    \item Use the returned inlier mask from RANSAC to filter matches for downstream disparity and depth computation.
\end{enumerate}

\subsubsection{Alternative Algorithm}
For alternative algorithms for image matching, two approaches will be implemented.
\paragraph{ORB: Feature Detector Summary}
First, I implemented an alternative pipeline that replaces the learned R2D2 detector 
with the classical ORB detector/descriptor. ORB (Oriented FAST and Rotated BRIEF) \cite{ORB} detects keypoints using the FAST corner detector applied on an image 
pyramid for scale robustness, and estimates a dominant orientation for each keypoint to obtain rotation invariance, and 
computes BRIEF-style binary descriptors on a rotated sampling pattern aligned to that orientation. The resulting 256-bit binary vectors are compact and 
extremely fast to match using Hamming distance; ORB also applies non-maximum suppression and keypoint scoring to retain stable points across scales, making 
it suitable for real-time or resource-constrained pipelines where learned descriptors may be too costly.
As ORB produces binary descriptors and keypoints with fewer metadata fields than R2D2, a small amount of code changes is required
to feed ORB output into the same downstream matching and depth estimation pipeline. The main changes are summarized below.

\paragraph{ORB: Code-level adaptations}
The following steps describe the minimal adapter implemented in \texttt{starter\_code\_feature.py}:
\begin{enumerate}
    \item Detect and compute ORB keypoints and descriptors:
        	\texttt{kp, desc = orb.detectAndCompute(img, None)}.
    \item Convert the list of \texttt{cv2.KeyPoint} objects to a NumPy array of pixel coordinates:
        	\texttt{pts = np.array([k.pt for k in kp], dtype=float)} (shape $N\times 2$).
    \item Extract a per-keypoint score from ORB's \texttt{kp.response}.
    \item A Hamming-capable matching method was introduced so binary descriptors from ORB can be matched natively without converting them to floating point.
    Specifically, the descriptors are kept as uint8 and matched with OpenCV's brute-force matcher (e.g. \texttt{cv::BFMatcher(cv::NORM\_HAMMING)}).
    I still applied Lowe's ratio test and an empirical distance threshold to remove weak matches.
    \item Initialize the defined \texttt{FeatureMatcher} with the adapted arrays: \texttt{FeatureMatcher(pts, desc, scores, ...)}.
\end{enumerate}

\paragraph{ORB: Evaluation}
ORB is faster but typically less robust than the learned R2D2 features in challenging illumination or viewpoint changes.
Parameters used: \texttt{distance\_ratio:0.9, distance\_threshold:45.0, ransac\_reproj\_thershold:1, confidence:0.99}  
\begin{itemize}
        \item Mean Absolute Error (MAE): 2.4556
        \item Root Mean Squared Error (RMSE): 4.6676
        \item Relative Error: 0.0795
\end{itemize}

\noindent The second alternative algirthm is to use a fully learned Graph-based neural-network framework \href{https://github.com/magicleap/SuperGluePretrainedNetwork}{SuperGlue} \cite{sarlin20superglue},
 that combines with an Optimal Matching layer that is trained to perform matching on two sets of sparse image features. In this network, it natively
 uses the output from \href{https://github.com/rpautrat/SuperPoint}{SuperPoint} \cite{DBLP:journals/corr/abs-1712-07629}, and to simplify the process, I'll use the demo script in SuperGlue's repository
 to produce keypoint pairs and descriptors.

 \paragraph{SuperGlue: Algorithm summary}
SuperGlue is a learned, graph-based matching module that replaces heuristic nearest-neighbour matching with a learned attention and optimal-matching stage. In short:
\begin{itemize}
    \item Input: two sets of sparse features \(\{(x_i,d_i)\}_{i=1}^N\) and \(\{(y_j,d'_j)\}_{j=1}^M\) (pixel coordinates and descriptors).
    \item Contextualization: descriptors are augmented with positional encodings and processed by self- and cross-attention layers to produce context-aware 
    descriptors \(c_i\) and \(c'_j\).
    \item Score matrix: a learned similarity produces scores \(S_{ij} = \exp\big(c_i^\top c'_j\big)\) (optionally with a learned linear projection and 
    temperature).
    \item Optimal matching: Sinkhorn normalization is applied to \(S\) to produce a (soft) doubly-stochastic matrix \(P=\text{Sinkhorn}(S)\). Discrete 
    matches are then taken as
    \[
      m(i) = \arg\max_j P_{ij}\quad\text{with}\quad P_{i,m(i)} > \tau_{\text{match}},
    \]
    and match confidence is given by \(\max_j P_{ij}\).
    \item Output: one-to-one consistent matches with per-match confidence; the learned module handles ambiguity and enforces global consistency better 
    than independent NN tests.
\end{itemize}
The approach is described in detail in the SuperGlue paper \cite{sarlin20superglue}. In this project we use the pretrained demo weights (``outdoor'') 
and the Sinkhorn-based matching with a small confidence threshold; the resulting matches are passed unchanged to the depth pipeline described above.

 \paragraph{SuperGlue: Code-level adaptations}

 Integration of SuperGlue into the pipeline was implemented as a separate module to avoid perturbing the existing detector/descriptor flow.
 \begin{enumerate}
    \item Batch invocation and file-format handling. I ran the provided demo script (\texttt{match\_pairs.py}) once over all image pairs (via a 
    \texttt{pairs.txt} file) so SuperGlue produces a set of \texttt{*.npz} outputs in a single output folder. Each \texttt{.npz} contains the arrays 
    \texttt{keypoints0}, \texttt{keypoints1}, \texttt{matches} and \texttt{match\_confidence}. A loader in \texttt{tools/superglue.py} 
    reads those files and extracts only the matches where \texttt{matches[i] > -1} and \texttt{match\_confidence[i]} exceeds a small confidence threshold.
    \item Adapter to the sparse depth pipeline. SuperGlue returns keypoint coordinates in pixel space and indices of matched points, so I converted those directly 
    to the pipeline's expected format: left/right pixel coordinates (u,v), compute disparity $u_L-u_R$, apply the same disparity / depth filters 
    (disparity $>0.1$, $0<z\le80$\,m), and write valid predictions to \texttt{P3\_result.txt}.
\end{enumerate}

\paragraph{Description of the ICP loss}
From Fig.~\ref{fig:10}, the ICP loss (mean Euclidean distance between corresponding point pairs) for all objects decreases sharply within the first five iterations. 
For the Armadillo and Bunny datasets, the loss stabilizes around 1 and 2, respectively, after approximately ten iterations. In contrast, the Dragon dataset 
exhibits a more gradual, nearly linear decline between the 5th and 25th iteration, reaching near zero by the 30th iteration. Additional iterations could be 
tested on the Dragon dataset to confirm whether it has fully converged or if further improvement is possible.

\paragraph{Explanation of the ICP loss}
The differing convergence behaviors in the ICP loss plots can be attributed primarily to variations in the point density of the target clouds, since the number of 
source point clouds for all objects are approximately 450, which can be excluded as a factor.
The Armadillo and Bunny datasets, each containing around 1400 target points, provide  dense coverage for ICP to quickly establish correspondences and 
converge within the first few iterations. In contrast, the Dragon dataset contains about 1200 target points, resulting 
in a sparser surface coverage. This reduced density limits the number of reliable correspondences, causing ICP to 
refine the alignment more gradually. Consequently, the dragon’s loss decreases in a slower, near-linear trend.

\paragraph{Description of the estimated 6D pose changes during ICP iterations}
From Fig.~\ref{fig:11}, the evolution of the estimated 6D pose during the ICP iterations shows that 
most translation updates occur within the first few iterations. For the armadillo and bunny datasets, 
the translation components (X, Y, Z) change sharply at the beginning as the source cloud aligns with 
the target’s global position, then quickly stabilize near zero, indicating convergence. In contrast, 
the dragon dataset displays persistent oscillations, especially along the X-axis, where the translation 
continues to vary even after 20 iterations.

\paragraph{Explanation of the estimated 6D pose changes during ICP iterations}
This behavior reflects the convergence dynamics of ICP. The rapid initial changes correspond to large corrective updates that reduce coarse misalignment, while the later 
stabilization indicates consistent correspondences and refined alignment. The fluctuations in the dragon dataset arise from its lower target point density that was
mentioned above, which limits the number of reliable correspondences. As a result, ICP 
requires more iterations and exhibits a less stable pose estimation process before convergence for the Dragon dataset.
